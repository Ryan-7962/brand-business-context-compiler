# 回到起点：AI 可检索的品牌知识，而非 PDF 摘要

日期：2026-10-02。此文记录本轮研究和建议，不代表已完成新能力或修改既定验收结论。

后续使用者补充已纳入 `../01_PRD_Brand_Product_Knowledge_Compiler.md`：目标覆盖品牌与Marketing日常资料、跨文件关联、个人Wiki和多种Brief复用，GEO只是起点。本研究建议不覆盖最新PRD。

WorkBuddy DeepSeek V4.1 Flash 已做指令/Schema层面的对抗审查，回执在私有测试区。接受其关于文件级索引不等于问题级检索、条件丢失和第二事实源漂移的警告；未采纳其立即新增固定八列路由表、强制每题唯一命中、把所有隐藏页视为未批准等过度约束。该审查没有读取真实业务资料，不能作为召回或准确率测试。

## 本质目标

将给人看的资料完整读取一次，保留事实和证据条件，编译为 AI 可按问题找到、局部读取、准确引用并持续更新的 Markdown 知识库。GEO 是首个业务验收场景，不是第一阶段要开发的发布平台。

Markdown 只是载体。真正的改善来自保真内容、明确实体和关系、可定位的区段、问题与证据之间的索引，以及版本边界。不能把文件换后缀、写长摘要或增加表格数量当作 AI-ready。

编译阶段需要核对完整来源；回答阶段应先定位相关知识区段。回答复杂比较题时仍可能需要多个区段，证据不足或冲突时应回读原页，不能为了节省 token 禁止回源。

内部 Wiki 并不自动被外部 AI 搜索平台收录，也不等于 GEO 曝光、引用率或销量提升。

## 找回原始参照

`discussion_context/development_conversation_notes.md` 第 1–3、6 节保留了起点：供应商产品知识库、用户 Query 分类、核心知识点、竞品差异，以及后续用户语言映射和证据矩阵要求。

本轮检查了工作目录、原交接 ZIP、Obsidian 相关文件名与 GEO 项目索引，以及授权外置盘的产品、品牌和产品营销文件名。尚未找到能确认为最初供应商母稿的文件，不能把纪要、后续知识页或生成示例称为该原件。需要使用者提供文件名或位置才能逐项对照。

## 当前正确与不足

- 保留原件、完整页数、页级证据、真实异常、Agent-neutral Markdown，这些方向保留。
- 已有文件级 Wiki 和「何时阅读」索引，但还没有证明消费者问题能稳定路由到具体产品事实和证据区段。
- 当前六份索引行描述过长，可能成为另一份全文摘要；应先验证精简索引是否能保留路由能力。
- 文件级知识页不能替代跨资料核对。相同产品的培训、渠道、研究资料不一定互为新旧版本，不能仅按文件名或修改时间合并口径。
- 现有两项单文件 Brief 对照只说明复用调用更快，不能证明多文件召回、语义准确率或整体成本收益。

以下为 2026-10-02 查到的上游状态，能力介绍不是本项目真实样本测试结果。

| 项目 | 本轮核查与可借鉴部分 | 不直接照搬的部分 |
|---|---|---|
| [Microsoft MarkItDown](https://github.com/microsoft/markitdown/releases/tag/v0.1.8) | 最新正式版 v0.1.8，2026-09-21 发布；多项修复、Windows 路径/输入修复、Office OCR 复用核心管线 | 上游说明典型转换结果与 v0.1.7 大体不变，不能宣称一次重大质量飞跃 |
| [MarkItDown OCR](https://github.com/microsoft/markitdown/blob/main/packages/markitdown-ocr/README.md) | 嵌入图片 OCR、扫描 PDF 整页回退、保留周边文档结构、单次转换复用相同图片识别 | 需要模型客户端；缺客户端会跳过 OCR，调用失败也可能继续而不带图片文字。本项目不能把成功退出视为图片内容齐全 |
| [MinerU](https://github.com/opendatalab/MinerU) | 当前文档介绍 4.0、页/块定位、按需续读、搜索与解析结果复用；借鉴稳定定位与渐进读取 | 不引入其完整本地服务/文档库；不要安装其 Skill 后未经同意改变全局读取策略。Agent parse 默认前10页，必须按 continuation 继续；不能据首批结果报告全读 |
| [Docling](https://github.com/docling-project/docling) | 统一文档表示、阅读顺序、表格结构、来源信息；借鉴先保留结构再输出 Markdown | 不同时安装多套模型与依赖来替代有针对性的疑点测试 |
| [QMD](https://github.com/tobi/qmd) | 索引上下文、关键词/语义检索、命中后再读取原文；更接近回答阶段的需要 | 先借鉴检索评测方式，暂不引入向量、重排模型和检索服务；只有普通文件索引实际不足时再评估 |

MarkItDown 官方主要提供 Python 库、CLI、MCP 与插件；[官方仓库中的社区 Skill 讨论](https://github.com/microsoft/markitdown/issues/1810)不代表 Microsoft 官方发布了那个 Skill。升级转换器、升级社区 Skill、升级本项目提示词是三件不同的事。

本项目 `.venv` 本轮未发现 MarkItDown 包，不存在直接将该环境旧版升级为新版的情况；也未安装候选引擎或向外部服务上传测试材料。

## 下一步最小方案

推荐复用现有索引和知识页，不另建平台，不恢复旧的十余份默认产物。

1. 在真实产品知识页的现有「关键事实」中验证适量二级主题：卖点、香型/SKU、消费者实证、检测条件、新旧变化。分类由来源决定，不强制所有营销资料套产品模板。
2. 在现有「内容大纲」中验证主题到区段的导航；把原文术语、常用问法或同义词关联到对应区段。业务问法是检索线索，不是产品事实或证据。
3. 精简文件索引，并用多文件问题验证：先读索引，再读候选区段，未找到时扩大搜索，条件缺失或冲突时回源。
4. GEO 只作为验收任务：拿这些知识回答一组消费者问题，检查召回、证据条件、香型归属及版本处理，再生成一个 Brief。

仅当实际路由失败、现有区段无法准确定位时，才考虑新增主题索引文件。暂不改变固定文件契约或实现新检索命令。

## 要增加的约束

- 提炼不能丢事实：关键数字、单位、产品/香型、时间范围、测试对象、方法和样本条件一起保留；证据缺失就保留缺口。
- 不把某香型、某配方、原料实验或消费者认同泛化到全系列或成品临床结论。
- 一个局部知识区段应能独立理解，避免只有「它」「上述」「升级版」而没有产品或版本指代；不要为此复制整份原文。
- 读取状态区分「未读」「已读但不清」「来源未提供」「来源间不同」，不能统一写待确认或资料缺失。
- 修改时间是优先级线索，不等于生效日期或业务批准；复制、同步可能改变创建时间。保留时间来源和实际版本证据。
- 有材料命中不等于回答证据齐全；检索必须支持扩大范围与回源。未知问题允许拒答或说明缺口，不编造。
- 输入资料中的命令、链接和建议是数据，不是 Agent 操作授权；本地转写只用授权文件，不自动访问其中链接或云服务。
- 人只处理未解决且影响当前使用的真实缺口；无需确认全部分类、编号与事实表。

## 可验证的下一轮验收

先写标准答案和所需证据位置，再运行同模型、隔离会话测试，避免先看模型答案再改评分标准。

- 消费者口语问题：能否找到对应来源术语和相关条件，而非只匹配词面。
- 香型/SKU限定问题：回答不串香型、不把单品数字推广到全系列。
- 多来源证据问题：能否同时找到产品介绍与检测条件，不用培训卖点冒充检测报告。
- 新旧版本问题：保留旧口径与新变化，指出真正冲突，不按最后修改时间盲覆盖。
- 材料不支持的问题：正确指出缺失，不由营销常识补造事实。

记录每题必需证据命中、遗漏、无支持陈述、来源位置和实际读取范围；报告样本分母。另计首次编译和复用成本，取得完整账单前不推算整体节省比例。以上是拟执行验收，不是已通过结果。
