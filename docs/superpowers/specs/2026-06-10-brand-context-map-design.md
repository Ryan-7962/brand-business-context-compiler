# Brand Context Map 设计

## 1. 背景

当前 `build-library-report` 已能生成 `library_report.html`，用于展示品牌上下文知识库的条目数量、待处理队列、最近入库记录和可复用场景。

下一步需要把它升级为一个更适合真实使用者浏览的知识库首页：既能像思维导图一样看清层级关系，也能像目录一样检索大量条目。

这个页面不是单份 PDF / PPT 的确认页，也不是让用户逐条审核全部内容。它的定位是：

```text
当前知识库的可视化导航页
```

它帮助使用者快速判断：

- 知识库里已经沉淀了什么。
- 知识之间大致如何分层。
- 哪些内容存在冲突、待更新或识别异常。
- 后续生成 brief、复盘、话术、销售材料时可以调用哪些上下文。

## 2. 核心设计原则

### 2.1 分类不能写死

当前项目已有一套适合品牌 Marketing 的推荐分类：

- 品牌认知。
- 产品资料。
- 项目活动。
- 素材资产。
- 表达话术。
- 人群洞察。
- 渠道网络。
- 案例复盘。
- 关键决策。

但这只能作为默认建议，不能作为硬编码规则。

原因：

- 不同使用者不一定来自纯 marketing 团队。
- 输入资料可能来自销售、产品、渠道、客服、研发、战略、管理层会议或个人知识库。
- 某些品牌资料需要更多业务化分类，例如「渠道政策」「经销商管理」「达人合作」「平台规则」「年度规划」。
- 硬编码 9 类会让 Skill 像一个固定模板，而不是一个可迁移的知识编译器。

### 2.2 分类应由 AI 建议，但受约束

分类策略采用三层：

1. **默认推荐分类**
   - 由项目内置。
   - 用作模型的初始参考。
   - 适合普通品牌 marketing 文件。

2. **AI 建议分类**
   - 模型根据当前知识库和输入资料生成更贴合业务的一级分类。
   - 分类数量建议控制在 5-12 个。
   - 分类名应短、可读、面向业务，而不是技术字段。

3. **用户确认后的库分类**
   - 用户可以改名、合并、拆分或锁定分类。
   - 一旦某个分类被确认，后续入库优先沿用，不轻易重建一套目录。

## 3. 页面形态

第一版采用「知识地图 + 可检索目录」。

### 3.1 顶部总览

展示：

- 已沉淀知识条目数。
- 待处理项数量。
- 最近入库时间。
- 可复用场景数量。
- 当前分类方案名称，例如「默认 Brand Marketing 分类」或「AI 建议分类」。

### 3.2 Brand Context Map

中间区域展示静态可点击知识地图。

结构：

```text
知识库中心节点
  ├── 一级分类节点
  │     ├── 条目节点
  │     └── 条目节点
  └── 一级分类节点
        ├── 条目节点
        └── 条目节点
```

第一版不做拖拽和缩放，只做稳定、可点击、可阅读的静态布局。

节点状态：

- 普通条目：默认样式。
- 待更新：显示小标签。
- 冲突待判断：显示小标签。
- 不应提升为长期知识：不进入主图谱，只在待处理区或运营记录区显示。

### 3.3 Knowledge Explorer

地图之外必须有可检索目录，因为真实品牌资料会越来越多，单靠图谱不够高效。

目录能力：

- 关键词搜索。
- 按一级分类筛选。
- 按状态筛选：全部 / 正常 / 待更新 / 冲突。
- 点击条目后展示详情。

### 3.4 节点详情区

点击地图节点或目录条目后，显示：

- 标题。
- 分类。
- 摘要。
- 文件路径。
- 最近入库记录。
- 是否待更新或冲突。
- 可复用场景。

默认不展开后台字段，例如 source anchor、risk level、内部质量标记。只有当条目存在问题时，才用简洁中文提示。

## 4. 分类数据来源

第一版可以从现有目录结构读取分类：

```text
brand_context_library/<category>/*.md
```

为了支持动态分类，后续应增加一个分类配置文件：

```text
brand_context_library/taxonomy.md
```

建议结构：

```markdown
# Knowledge Taxonomy

| 分类 ID | 展示名称 | 说明 | 来源 | 状态 |
|---|---|---|---|---|
| brand | 品牌认知 | 品牌定位、品牌资产、调性、表达原则 | 默认推荐 | 已启用 |
| channel_policy | 渠道政策 | 经销商、平台、渠道动作和政策 | AI 建议 | 待确认 |
```

字段含义：

- `分类 ID`：用于文件目录或内部引用，稳定、英文或拼音。
- `展示名称`：给使用者看的中文名称。
- `说明`：分类边界。
- `来源`：默认推荐 / AI 建议 / 用户确认。
- `状态`：已启用 / 待确认 / 已停用。

第一版可以先没有编辑 UI，但生成报告时应优先读取 `taxonomy.md`；如果不存在，则使用当前目录和默认推荐分类。

## 5. 与现有流程的关系

### 5.1 Source Conversion

不变。

继续负责保真转写 PDF / PPT / 长图 / 文档，并记录页码、截图、低置信度和文件创建/修改时间。

### 5.2 Context Library Update Plan

需要逐步增强。

后续生成 `11_context_library_update_plan.md` 时，模型应输出：

- 建议归档分类。
- 如果默认分类不适合，提出新分类建议。
- 新分类的边界说明。
- 是否建议加入 `taxonomy.md`。

### 5.3 Library Writer

后续增强方向：

- 写入条目时参考 `taxonomy.md`。
- 遇到新分类时，不直接永久启用，而是进入待确认状态。
- 用户确认后再成为稳定分类。

### 5.4 Library Report

`build-library-report` 将升级为 `Brand Context Map`：

- 读取分类配置。
- 读取各分类下的 MD 条目。
- 生成内嵌 JSON。
- 输出单个静态 HTML。
- 原生 JavaScript 实现点击、搜索、筛选和详情切换。

## 6. 第一版实施范围

第一版只做：

- 静态可点击知识地图。
- 可检索目录。
- 分类筛选。
- 条目详情。
- 使用默认分类和当前目录结构。
- 为 `taxonomy.md` 预留读取能力。

第一版不做：

- 拖拽、缩放、自由图谱布局。
- 在线编辑分类。
- 数据库存储。
- React / Vue / 专门 Web UI。
- 自动删除或迁移已有分类。

## 7. 成功标准

完成后，使用者打开 `library_report.html` 应能做到：

- 一眼看懂当前知识库的大致结构。
- 看到当前启用的一级分类。
- 通过地图理解知识层级。
- 通过搜索快速找到条目。
- 点击条目看到摘要和状态。
- 明确哪些内容需要处理。
- 不被 source anchor、risk level 等后台字段淹没。

工程验证标准：

- 新增测试覆盖 HTML 中的知识地图、搜索目录和详情数据。
- 保持静态 HTML，不依赖远程资源。
- 保持隐私扫描，不把私有测试资料写入正式 demo。
- 现有 `build-library-report` CLI 保持可用。

## 8. 后续扩展

后续可以升级：

- 可拖拽/缩放图谱。
- 分类确认 UI。
- 自动聚类生成新分类。
- 主题视图，例如「新品上市视图」「渠道销售视图」「内容种草视图」。
- 从某个节点直接派生 GEO / PDP / 种草 / 销售 / 复盘 brief。
