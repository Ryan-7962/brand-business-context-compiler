# Project Goal｜Brand / Business Context Compiler

更新日期：2026-07-10

## 1. 最终目标

本项目要形成一个本地优先、由 AI 驱动的 Brand / Business Context Compiler：把品牌、Marketing、销售、渠道、产品、会议、策略、Campaign、培训、复盘、投放、竞品、科研或功效检测报告等“原本给人看的资料”，编译成可被不同 AI Agent 稳定读取、检索、引用和持续更新的 Markdown Wiki。

它不是普通 PDF / PPT 摘要工具，也不是企业级 RAG、正式 Web App 或下游内容生成平台。

项目采用以下使用定位：

- **Codex-first**：Codex 是当前主要开发、测试和个人使用环境。
- **WorkBuddy-compatible**：腾讯 WorkBuddy 是主要同事分发和办公使用环境，第一阶段必须验证 Skill 能被真实导入和调用。
- **Agent-neutral Wiki**：Markdown Wiki 是长期资产，不绑定 Codex、WorkBuddy 或某个特定模型。
- **其他 Agent 可兼容**：Claude、ChatGPT 等可以读取同一 Wiki，但第一阶段不逐一开发专用适配。

核心链路是：

```text
Raw Sources
→ Source-to-Markdown
→ AI Semantic Compilation
→ Agent-neutral Structured Wiki
→ Codex / WorkBuddy 按任务调用
```

## 2. 什么时候值得使用

本项目不假设 Structured Wiki 在所有场景都优于直接读取 PDF / PPT。

### 适合直接交给 Agent 的场景

- 只有一份简单文件。
- 只做一次性问答或摘要。
- 文件版本清楚，不需要长期保存和重复调用。
- Agent 已经能完整读取文件中的正文、图片和表格。

这类场景不应强制运行完整 Compiler。

### 适合使用 Compiler 的场景

- 同一任务涉及多份产品、品牌、竞品、渠道、内容或检测资料。
- 同一项目存在多个版本，需要识别更新时间和内容冲突。
- 同一批资料后续会反复用于 GEO、PDP、种草、拍摄、销售或复盘等任务。
- 需要知道结论来自哪个文件、哪一页或哪一张 slide。
- 需要把一次性项目资料逐步沉淀为长期品牌知识。
- 需要在 Codex 与 WorkBuddy 等不同 Agent 之间复用同一套上下文。

本项目的价值假设是：在这些多文件、多版本、重复调用场景中，Structured Wiki 应减少漏读、版本混淆、重复读取和无法追溯的问题。该假设必须通过真实任务验证，不能预先当作结论。

## 3. 三层架构

### Layer 1｜Raw Sources

使用者把原始资料放入项目文件夹：

- PDF / PPT / PPTX / DOCX / Markdown / TXT。
- 产品介绍、产品培训、品牌策略、Campaign 方案、广告公司提案、销售策略和会议资料。
- 过往 brief、内容复盘、竞品资料、投放总结、科研或功效检测报告。

Raw Sources 是事实源：

- 不改写、不覆盖原文件。
- 记录文件名、创建时间、修改时间和转写时间。
- 多版本并存时，更新文件只作为更高优先级线索，不自动覆盖旧知识。
- 原文件始终保留为最终核对依据。

### Layer 2｜Agent-neutral Structured Wiki

这一层分成两个不同职责，不能混为一谈。

#### A. 确定性资料处理

- 盘点全部输入文件。
- 尽量保真地转成 Markdown。
- 保留文件、页码、slide 和截图锚点。
- 核对总页数、已读取页数和异常页。
- 记录文件时间、疑似版本和转换方式。

#### B. AI 语义编译

- 识别每份文件实际讲什么，而不是只按关键词套固定分类。
- 生成文件大纲、核心观点、关键事实和业务关系。
- 区分来源事实、AI 归纳、资料缺失和待确认内容。
- 生成后续 Agent 能按需读取的索引和知识页。
- 不把会议讨论、代理商建议或来源中的“确认”字样自动升级为品牌确认口径。

长期 Wiki 至少应让 Agent 回答：

1. 当前有哪些资料？
2. 每份资料大概讲什么？
3. 当前任务应该优先读取哪些知识页？
4. 关键事实来自哪个原文件和页面？
5. 哪些内容存在版本冲突、识别异常或资料缺失？

### Layer 3｜Agent Outputs

Codex、WorkBuddy 或其他 Agent 可以基于 Wiki 生成：

- GEO / PDP / 种草 / 拍摄 brief。
- 销售话术、客服 FAQ 和渠道材料。
- 投放复盘、竞品分析和品牌策略总结。

这些属于下游应用，不是第一阶段默认开发内容。第一阶段只保证 Wiki 足够可靠、可索引、可追溯和可移交。

## 4. 最终交付形态

本项目最终不是单一软件，也不是只有一份 `SKILL.md`，而是一个可移植的轻量工作包：

1. **Skill 包**：告诉 Codex / WorkBuddy 何时调用、如何读取资料、如何完成 AI 语义编译。
2. **本地轻量工具**：负责确定性的文件盘点、格式转换、锚点、页数和版本记录。
3. **Markdown Wiki**：真正长期保存、跨 Agent 复用的知识资产。
4. **中文 HTML 报告**：只用于查看本次读取概况、Wiki 层级和真正需要处理的异常。

第一阶段不要求同事理解 Python、CLI、Schema、Fact ID、风险等级或后台校验字段。技术细节可以保留在后台，但不能成为普通使用者的操作负担。

## 5. 第一阶段最小边界

### 第一阶段必须完成

- 一个推荐入口完成从资料文件夹到 Structured Wiki 的主流程。
- PDF / PPTX / DOCX / Markdown / TXT 的基础读取与来源追溯。
- 每份文件都有可读的 Markdown 转写稿和 AI 语义知识页。
- 一个批次总索引，告诉 Agent 该读什么、去哪里读。
- 一个异常清单，只列确实没读清、缺页、冲突或缺资料的内容。
- 一个中文 HTML 概览，展示批次内容、知识层级和异常。
- Codex 中真实运行通过。
- WorkBuddy 中完成一次 Skill 导入和真实资料包调用测试。

### 第一阶段不做

- 正式 Web UI。
- 企业级 RAG、向量数据库或复杂数据库。
- 多用户权限、在线协作和云端管理后台。
- 复杂模型 API 编排。
- 自动品牌确认、自动外发或合规审批。
- GEO、PDP、种草等完整下游生成系统。
- 为每一种 Agent 单独维护一套实现。
- 为未来可能需要的场景增加命令、分类、报告或配置。

## 6. 人工介入原则

人工确认采用异常驱动，不要求逐条审查全部 Markdown。

系统应先自动完成读取、转写、AI 语义编译和索引。只有以下情况需要使用者处理：

- 文件大纲或主题识别明显错误。
- 页面、slide、表格、图片、小字、截图或 OCR 区域没有读清楚。
- 总页数、已读取页数和缺失页数不一致。
- 关键事实没有来源、与旧知识冲突或版本关系不清楚。
- 任务必须使用某项信息，但资料本身没有提供。

中文报告只需要回答：

1. 这次读了哪些文件，每份大概讲什么？
2. 生成的 Wiki 大纲和知识层级是什么？
3. 哪些页面或内容确实没有读清楚？
4. 需要重新提供截图、补原文件、换转换方式，还是人工补录？

## 7. 真实性与隐私原则

- 有 18 页就必须记录 18 页的读取状态，不能只读 16 页却报告完整。
- 没有数据就写“资料未提供”，不能编造数字、结论或品牌口径。
- OCR、图片、表格和小字没有读清楚时必须明确标记。
- AI 归纳与推断必须和来源事实区分，不能冒充品牌确认。
- 原始文件始终是事实核对依据，Wiki 不能覆盖或替代原文件。
- 真实品牌测试资料只进入本地私有测试区，不进入公开 examples、docs、prompts、schemas 或 README。
- 给同事分发的 Skill 包不得包含测试品牌名称、商业数据或私有文件内容。

## 8. 第一阶段验收标准

### A. 文件完整性

- 输入目录中的每个支持文件都出现在 source index 中。
- PDF 总页数、PPT slide 数和实际生成的页面锚点一致。
- 每份文件都有创建时间、修改时间、转写时间和来源路径。
- 未读页面和不支持文件必须明确报告，不能静默跳过。

### B. AI 语义结果

- 每份文件都有与原资料主题一致的大纲、概述和核心内容。
- 语义知识页由 Agent 基于完整转写稿生成，不能只依靠固定关键词分类器冒充 AI 理解。
- 关键事实能够回到原文件和页面锚点。
- 资料未提供、AI 推断和来源事实具有清晰不同的状态。

### C. 使用体验

- Codex 能通过一个推荐入口完成真实资料包编译。
- 普通使用者只需要查看批次索引、知识页、异常清单和中文 HTML。
- WorkBuddy 能导入 Skill 包，并对同一份 Structured Wiki 完成至少一个真实办公任务。
- 第一阶段不要求使用者手动串联大量 CLI 命令或逐个确认后台文件。

### D. 价值验证

- 不要求在单份简单 PDF 场景中证明 Wiki 优于直接读取。
- 至少选择一个多文件、多版本、会被重复调用的真实任务进行对照。
- 对照只评价四项：信息完整性、来源可追溯性、版本处理、再次调用成本。
- 如果 Structured Wiki 没有明显改善，应记录结果并继续简化，而不是增加更多功能证明项目合理。

### E. 工程与隐私

- 核心测试和基础编译检查通过。
- 私有资料没有进入 Git 跟踪或公开 Skill 包。
- 主流程失败时明确报告真实原因，不生成虚假完成状态。
- Git 提交记录能够说明每次必要改动。

## 9. 当前阶段与下一步

第一阶段已于 2026-07-11 完成：用户可见产物已收缩为批次索引、每文件知识页、异常清单和中文 HTML；真实多文件、知识版本演进、重复调用、Codex 与 WorkBuddy 均已验证。

当前冻结新功能。下一步不是继续扩建系统，而是把现有 Skill 用于真实工作；只在真实使用暴露明确问题时修复最小缺口。GEO、PDP、种草等下游 Skills、企业级 RAG 和正式 Web App 仍不属于第一阶段。
